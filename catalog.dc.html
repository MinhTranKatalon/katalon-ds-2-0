Colors

Three color rules

No new colors. Same palette, jobs reassigned: a neutral canvas, blocks in any hue, green returned to action.

Specimen · the page canvas is neutral

The page canvas — the base background the whole website sits on — uses exact Neutral ramp values only (gray-0 · 50 · 100), never a value outside the ramp. No Katalon brand color becomes the overall background of a page. The two dark steps gray-800 · 900 are a restricted canvas: special pages only — events, campaign landings, print — not the everyday website or product UI. Everything placed on that canvas may use brand color — sections, banners, cards, callouts, badges, charts, illustrations, tint or solid — within two limits: never Forest 600 as a card, section or page fill, and at most 2–3 strong boxes per page — counting only saturated 600 and deep 800–950 boxes; pastel 50–300 boxes don't count. The neutral canvas is what lets those blocks read as deliberate accents instead of a wall of brand.

How to use background color

One neutral canvas, held steady from top to bottom, with colored sections and cards laid on top. “How you use it” matters more than “which color you may use”.

Principle: the canvas stays one neutral tone for the whole page. Color enters as a rounded-corner box — a banner, a section, a card — with a visible edge and the neutral canvas still showing around or between boxes. Never use edge-to-edge color bands to divide the page.
Product UI (app)

A single neutral canvas for the whole app, unchanged across screens — gray-50. Cards and panels sit on a gray-0 fill. Tints appear only in callouts, selected rows, status regions — never re-tint a whole screen per module.

canvas → gray-50 · card → gray-0 · zone → tint-50
Website (marketing)

Canvas is gray-0 (or gray-50) for the whole page. On top of it, sections and banners may take brand color — a tint 200–300 box, a forest 800–950 or solid 600 box, a colored card grid. Steps 50–100 stay callouts, notes and badges — small elements with a border. They are not section or card fills: at 1.01–1.18:1 against the ground a large box has nothing to read. Keep it to 2–3 strong boxes per page (600 and 800–950; a 200–300 tint doesn't count) so the canvas still reads through.

canvas → gray-0 / gray-50 · section → tint 200–300 or solid box · 2–3 strong boxes max · tint doesn't count
Do
  • Keep the page canvas on an exact Neutral value — gray-0, gray-50 or gray-100.
  • Make colored sections, banners and cards rounded boxes, and let the canvas show around them.
  • Limit a page to 2–3 strong boxes — count 600 and 800–950 boxes; pastel 50–300 boxes don't count. The rest stays neutral.
  • Measure contrast on every colored box — body copy ≥ 4.5:1, button fill ≥ 3:1.

  • Use a gray-800 / 900 canvas for the everyday website or product UI — events and print only.

Icons

UI icons are line glyphs: a 24px grid, stroke 1.4, round caps and round joins everywhere — every corner is a radius and every terminal is a rounded cap, never a square cut or a hard vertex — and never a fill. Strokes inside one glyph never touch: anything overlapping is notched out of the shape below it, leaving a gap as wide as the stroke itself. They ship as inline SVG (or a sprite) from the DS icon set — no icon font, no hand-drawn glyphs. Solid is reserved for Product marks (rounded square on a pastel tile). Icons inherit currentColor, so any brand hue is allowed as long as the stroke measures ≥3:1 against its ground.

Mandatory rules

Eight rules, and none of them is a preference. An icon that breaks one is not a variant — it is a different icon set, and two sets in one product is what makes an interface feel unowned. Nobody edits these per screen, per squad or per deck.

01
Line only — never a fill
A UI icon is an outline. A solid shape is a Product mark and nothing else, so a filled glyph in a toolbar reads as a product, not an action.
02
24px grid, stroke 1.4, unchanged
Drawn on the 24 grid and rendered at 16 · 20 · 24 · 32 — the only sizes a UI icon ships at. The stroke stays 1.4 at every one of them: no thickening, no faux bold. The one exception is a glyph set inline in running text (a callout, a sentence, a caption), which is optically matched to that text and never goes below 12px.
03
Round caps, round joins
Every terminal is a rounded cap and every corner is a radius. No butt caps, no miter joins, no hard vertex anywhere in the set.
04
Strokes never touch
Where shapes overlap, the one underneath is notched open by one stroke width (1.4u). The notch is cut into the outline — never a shape filled with the background colour.
05
One colour, inherited
The glyph takes currentColor from the row or button it sits in. Any brand hue is allowed at ≥3:1. No gradients, no two-tone glyphs, no per-state recolouring inside the icon.
06
A background is a circle
When a UI icon needs a ground it is a circle — neutral gray or a pastel of any brand hue. The rounded square is reserved for Product glyphs.
07
Only glyphs from the set
No icon font, no emoji, no Unicode symbol as a glyph, nothing drawn inline for one screen. If a glyph is missing, add it to the DS set and regenerate — that is the only way the set grows.
08
Never the only signal
Every icon-only control carries an aria-label, and every status icon carries its word. An icon alone never conveys meaning, and colour alone never conveys state.
Telling them apart — background shape + color
Ordinary icons (UI)
Neutral by default; icon and circle may take any brand hue that measures ≥3:1 against its ground. Always a line glyph. If a UI icon has a background, the shape MUST be a circle.

Clearance · strokes never touch

Two strokes in one glyph never run into each other. Where a shape sits on top of another — a status badge, a method plate, any overlay — the shape underneath is cut open to leave a gap equal to the stroke weight — 1.4u on the 24 grid, the same 1.4 the glyph is drawn with, so the empty space reads as deliberate at every size. The gap is a notch in the outline itself, never a shape filled with the background colour: a cover shape breaks the moment the glyph is exported or dropped on another ground.

Token architecture

A two-layer token system. The core layer holds every real value — 8 ramps × 11 steps, no meaning attached. The semantic layer assigns roles and encodes the three color rules: a neutral canvas, blocks in any hue, and green returned to action. Product UI and Website read the same semantic names; only what a block may resolve to differs by surface.

Token precedence · which file wins
Two stylesheets define about 70 of the same --k-* names with different values. ds/katalon-ds.css loads last, and its values are the DS 2.0 contract.
  • Neutral greys are green-tinted here; plain greys in the other file.
  • --k-text-link and --k-focus-ring are Forest Green here, the legacy blue #5959EB there.
  • Every --k-shadow-* is none here — the other file still carries real shadows.
So: never load katalon-ds.css before the other stylesheet — links would turn blue and shadows would come back, with nothing on screen to explain why. And a page that loads only the marketing bundle is not on DS 2.0.
